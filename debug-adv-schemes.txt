  For ATS-enabled models, sim_grp.delt (tdis.delt) is fixed for the whole
  timestep — MF6 only shrinks it between outer timesteps (via
  finalize_time_step/next get_time_step), never mid-Picard-loop. So when
  convergence keeps failing, the ATS branch's while sim_grp.delt > mindt
  condition never becomes false and kiter is never checked, meaning mf6.solve()

  giving up after maxiter (100) tries like the non-ATS branch does, and letting

● Summary

  Root cause found without needing a native MF6 debug build: the crash wasn't in
  MODFLOW6 itself — it was a missing iteration cap in
  modflowapi/extensions/runner.py. The ATS (adaptive time-stepping) branch of
  run_simulation's solve loop had while sim_grp.delt > mindt: with no bound on
  Picard iterations, unlike the non-ATS branch's while kiter < maxiter:. Since
  MF6 only shrinks delt between outer timesteps (not mid-loop), a timestep that
  failed to converge would get mf6.solve() called on it indefinitely, feeding an
  already-unstable solution back into itself over and over.

  How we localized it (all from the Python side, no WinDbg/debug MF6 build
  needed):
  1. Reproduced with pytest test_mf6_examples.py -k ex-gwt-adv-schemes -v -s run
  from autotest/ (the relative libmf6 path only resolves from there).
  2. Grepped the full log for "Copying" blocks to identify the actual failing
  model — it was gwt_voronoi_square-wave_central (a GWT transport model using
  the "central" advection scheme, numerically unstable for a sharp square-wave
  front), not the first model in the list as it first appeared.
  3. Wrote a standalone script that ran the flow prerequisite (gwf_voronoi) then
  drove run_simulation directly with a diagnostic callback dumping sim.kstp,
  sim.delt, sim.iteration, and model.X (concentration) every Picard iteration.
  4. That showed kstp stuck at 304 for 5000+ iterations with delt never moving
  and concentration diverging to ~1e10 magnitude — proof the loop was unbounded
  and the model was in numerical runaway, eventually corrupting memory deep in
  the Fortran solve routine.

  The fix: one-line change adding and kiter < maxiter to the ATS while-loop
  condition (runner.py:91), so a non-converging ATS timestep now gives up after
  the configured OUTER_MAXIMUM tries and lets MF6's real ATS logic shrink dt on
  the next attempt — same as the non-ATS path already did.

  Verified:
  - test_mf6_examples.py -k ex-gwt-adv-schemes — now passes (previously
  access-violation crash).
  - test_interface.py (12 tests, including test_ats_model) — all pass,
  confirming normal ATS convergence still works.

  The concentration field for that particular model/scheme combo still diverges
  physically (central-differencing instability for a sharp front is a known
  limitation of that scheme, not a bug), but it now fails gracefully via MF6's
